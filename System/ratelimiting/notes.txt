RATE LIMITING
Why systems must limit traffic
Systems must limit traffic to protect themselves from overload. Resources like CPU memory database connections and network bandwidth are limited. Without limits a sudden spike or abuse can consume everything and crash the system. Rate limiting keeps the system stable by controlling how much work it accepts at one time.
How different rate limiting algorithms work
Rate limiting algorithms define how requests are counted and allowed. Fixed window allows a set number of requests per time window but causes bursts at window edges. Sliding window smooths this by tracking requests over time. Token bucket adds tokens at a steady rate and allows short bursts. Leaky bucket processes requests at a constant rate and queues or drops excess traffic.
How distributed rate limiting is done
In distributed systems many servers handle requests at the same time. Rate limits must be shared across them. This is usually done using a central store like Redis to track counters or tokens. Each request checks and updates this shared state. Consistency and latency are challenges so designs often trade strict accuracy for speed.
Where rate limiting protects systems
Rate limiting protects APIs from abuse bots and denial of service attacks. It prevents a single user or service from exhausting shared resources. It also protects downstream systems like databases and third party APIs. Internal rate limits stop cascading failures between microservices.
